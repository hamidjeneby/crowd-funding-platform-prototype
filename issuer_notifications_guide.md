# Issuer Notification System Architecture & Implementation Guide

This document details the database schema, event triggers, threshold evaluation logic, real-time listeners, UI components, and developer guidelines for the **Issuer Notifications** engine in the Crowd Funding Platform.

---

## 1. Database Schema

### `issuer_notifications` Table
Stores notifications directed at corporate issuers, generated by platform auditor compliance reviews, investor pledging activities, and milestone verifications.

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `BIGINT` (PK) | Unique notification identifier |
| `issuer_id` | `BIGINT` (FK -> `issuers.id`) | Recipient issuer profile internal ID |
| `type` | `TEXT` | Event category code (e.g. `pledge_recieved`, `funding_threshold`, `milestone_rejected`) |
| `title` | `TEXT` | Concise user-facing headline |
| `message` | `TEXT` | Actionable message body |
| `notification_text` | `TEXT` | Unique event key used for deduplication (e.g. `50_percent_funded`, `soft_cap_reached`) |
| `requires_action` | `BOOLEAN` | `true` if the notification requires the issuer to take action; otherwise `false` |
| `action_url` | `TEXT` | Relative portal URL where the issuer can complete the required action (e.g. `/issuer-portal/account`) |
| `read_status` | `BOOLEAN` | `false` when created (unread); updated to `true` when viewed, dismissed, or clicked |
| `created_at` | `TIMESTAMPTZ` | Timestamp when the notification was created |

## 2. Supabase Realtime Configuration

For client-side components to receive instant WebSocket updates when new notifications are inserted, the `issuer_notifications` table must be included in Supabase's Realtime publication.

### SQL Setup Query
Run this query in the **Supabase Dashboard -> SQL Editor**:

```sql
-- Enable Realtime WebSocket broadcast for issuer_notifications table
ALTER PUBLICATION supabase_realtime ADD TABLE issuer_notifications;
```

> **Polling Backup**: Even before running this query or during network reconnects, the issuer interface utilizes a 4-second polling fallback (`setInterval(loadNotifications, 4000)`), guaranteeing that notifications appear automatically without requiring manual page reloads.

## 4. Pledge & Threshold Evaluation Logic

When an investor pledges into a project (`createPledge` in `app/actions/pledge.js`), the platform performs an asynchronous evaluation via `notifyIssuerPledgeAndThresholds(projectId, newPledgeId)`:

### 4.1 Immediate Pledge Notification
A `pledge_recieved` row is inserted for the project's issuer on every valid pledge:
- **Title**: `New Pledge Received: {Project Title}`
- **Message**: `An investor has pledged {Currency} {Amount} into "{Project Title}".`

### 4.2 Boundary Crossover Mathematics
Funding thresholds and caps are evaluated by comparing the cumulative pledged total **before** and **after** the incoming pledge:

$$\text{Total Before} = \text{Total After} - \text{Incoming Pledge Amount}$$

A milestone threshold $T$ is triggered if and only if:
$$\text{Total Before} < T \quad \text{AND} \quad \text{Total After} \ge T$$

#### Supported Threshold Boundaries:
1. **50% of Target Goal**: $T_{50} = 0.50 \times \text{target\_goal}$ (`notification_text: "50_percent_funded"`)
2. **100% of Target Goal**: $T_{100} = 1.00 \times \text{target\_goal}$ (`notification_text: "100_percent_funded"`)
3. **Soft Cap**: $T_{\text{soft}} = \text{soft\_cap}$ (`notification_text: "soft_cap_reached"`)
4. **Hard Cap**: $T_{\text{hard}} = \text{hard\_cap}$ (`notification_text: "hard_cap_reached"`)

### 4.3 Deduplication Rule
Before inserting a threshold alert (`funding_threshold`, `soft_cap_reached`, or `hard_cap_reached`), the system queries the `issuer_notifications` table to check if a row with the matching `notification_text` already exists for this project. If found, duplicate insertion is avoided.

### 4.4 Example Walkthrough

Consider a project with:
- **Target Goal**: \$100,000 (50% = \$50,000, 100% = \$100,000)
- **Soft Cap**: \$75,000
- **Hard Cap**: \$150,000

| Step | Pledge Amount | Total Before | Total After | Notifications Generated | Reason |
| :---: | :---: | :---: | :---: | :--- | :--- |
| **1** | \$20,000 | \$0 | \$20,000 | `pledge_recieved` | First pledge recorded. No threshold crossed. |
| **2** | \$35,000 | \$20,000 | \$55,000 | `pledge_recieved`<br>`funding_threshold` (50%) | \$50,000 (50%) was crossed between \$20,000 and \$55,000. |
| **3** | \$25,000 | \$55,000 | \$80,000 | `pledge_recieved`<br>`soft_cap_reached` | \$75,000 (Soft Cap) was crossed between \$55,000 and \$80,000. 50% was already crossed previously. |
| **4** | \$70,000 | \$80,000 | \$150,000 | `pledge_recieved`<br>`funding_threshold` (100%)<br>`hard_cap_reached` | Both \$100,000 (100%) and \$150,000 (Hard Cap) boundaries were crossed by this pledge commitment. |

## 5. UI Architecture & Interaction Flow

### 5.1 Stacked Toast Deck (`IssuerToastNotificationStack.jsx`)
- Mounted globally in `IssuerPortalLayoutClient.jsx` (top-right screen corner).
- Features layered visual stacked cards with counter badge (`1 of N`).
- **Dismiss Button ('X')**: Always present on every notification card. Clicking it immediately dismisses the card and sets `read_status = true` in Supabase.
- **Action Button**: Displayed on notifications where `requires_action === true`.
  - Styled with high-contrast accent styling and an external action link icon.
  - Clicking the action button:
    1. Sets `read_status = true` in the database.
    2. Dismisses the toast card immediately.
    3. Navigates the issuer directly to the target `action_url`.
- **"Dismiss All" Button**: Sets `read_status = true` for all unread notifications.
- **Expand / Stack Toggle**: Allows expanding into a full vertical deck with scrolling.

### 5.2 Notifications Center (`/issuer-portal/notifications`)
- Full database-driven activity center fetching from `issuer_notifications`.
- Filterable tabs:
  - **All Notifications**
  - **Action Required** (filtered strictly by `requires_action === true AND read_status === false`)
  - **Reviewer Decisions** (KYB, Bank, Project)
  - **Milestone Outcomes**
  - **Campaign Funding** (50%, 100%, Soft Cap, Hard Cap, Pledges)
- **Action Button Visibility**:
  - The "Take Action" button is displayed **only** if `requires_action === true` **and** `read_status === false` (unread).
  - Once a notification is marked as read or clicked, the "Take Action" button is hidden to prevent duplicate or stale actions.
- **Action Required Queue Logic**:
  - Notifications where `read_status === true` are excluded from the Action Required tab and queue count.
  - When marked read, notifications seamlessly transition out of the Action Required queue.
- **Silent Background Sync & Anti-Flicker**:
  - Supabase Realtime WebSocket listeners and periodic fallback polling execute silent background revalidation (`isSilent: true`).
  - Skeleton screens and loading states only display on initial mount or explicit user tab/page transitions, eliminating random flashing and flickering on the notifications page.
- "Mark Read" and "Mark All as Read" capabilities.
